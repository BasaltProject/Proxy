# Relay benchmark, 2026-10-16

Reproduce: start an offline Basalt Server with room for the bots, then

    python3 tools/bench-relay.py --proxy build/release/bin/BasaltProxy-<version> --swarm <BasaltSwarm> \
        --backend-port <port> --output build/integration/bench-relay --count 50 --window 20 \
        --versions 26.3,26.2,1.21.4,1.19.4

For each client version it connects `count` Swarm bots (no physics) through the proxy, waits until they are all in play, then reads
the proxy's relay byte counters (console `status`) and its CPU seconds before and after a `window` second interval.

Setup: 8 logical CPUs, Linux 6.12.107, clang 19.1.7, proxy built with the release preset, Basalt Server and Swarm debug builds, one host,
loopback, offline, forwarding none, no plugins, 50 bots per run, 20 s window.

| Client | Sessions | Bytes toward clients | Proxy CPU (percent of one core) |
|---|---|---|---|
| 26.3 (native, no translation) | 50 | 1,260 kB/s | 27.8 |
| 26.2 (translated) | 50 | 589 kB/s | 16.2 |
| 1.21.4 (translated) | 50 | 780 kB/s | 22.7 |
| 1.19.4 (translated, no configuration phase) | 50 | 333 kB/s | 29.0 |

Proxy peak RSS over the four runs: 27,480 kB. Bytes toward backends were below 0.1 kB/s in every run (only keepalive replies).

Reading with care: the byte rates are what the backend chose to send each client in that window and the translated rows carry fewer
bytes because the translation drops or reshapes packets, so the rows are not comparable as throughput. The CPU column is the useful one:
on this host the proxy used between 16 and 29 percent of a core for 50 clients in play, translated clients included, and 1.19.4
cost the most per byte moved. The backend is a debug build, bots and backend share the CPUs with the proxy, and each cell is a single
20 second sample. No comparison with Velocity or any other proxy was run and none is claimed. Not measured: more than 50 clients, large
chunk bursts, slow receivers, TLS or online authentication, multiple backends, other platforms.
