# Login benchmark, 2026-10-16

Reproduce: start a Basalt Server (offline, loopback, max-players above the bot count) and run

    python3 tools/bench-login.py --proxy build/release/bin/BasaltProxy-<version> --swarm <BasaltSwarm> \
        --backend-port <port> --backend-log <server stdout log> --output build/integration/bench-login \
        --count 100 --delay 10 --rounds 3

What it measures: wall time from the first bot until the backend has logged `count` joins, direct to the backend and then
through the proxy, plus the proxy's own CPU seconds (utime + stime) and peak RSS. Bots are the independent Swarm client
(Basalt 26.3, no physics), spaced `delay` ms apart, so the floor is count x delay (1.0 s here).

Setup: 8 logical CPUs, 11.7 GiB RAM, Linux 6.12.107, clang 19.1.7, proxy built with the release preset, Basalt Server and
Swarm debug builds, all on one host over loopback, offline mode, forwarding none, no plugins.

| Path | Round 1 | Round 2 | Round 3 | Proxy CPU per 100 logins |
|---|---|---|---|---|
| Direct to backend | 8.66 s (warm-up) | 3.48 s | 3.48 s | - |
| Through the proxy | 4.91 s | 4.72 s | 4.83 s | 1.27, 1.36, 1.48 s |

Proxy peak RSS over the six rounds: 28,012 kB. Every round joined all 100 bots.

Reading: about 1.3 s more wall time and 13 to 15 ms of proxy CPU per login on this setup. The backend is a debug build and
dominates both paths, and the two share the CPUs with the bots, so the figures say what the proxy costs here, not what
it can sustain. No comparison with Velocity or any other proxy was run and none is claimed.

Not measured: relay throughput once in play, translated clients, online authentication, TLS, a release backend, other
platforms, long runs, tail latency.
